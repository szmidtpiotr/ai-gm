## 1. Executive Summary

This is a vulnerability assessment of the AI-GM web application (`https://aigm-dev.studio-colorbox.com`), a development instance. Testing covered the client-side code, HTTP configuration, unauthenticated API behaviour, and — using an owner-supplied test account (`wojtek`, a non-admin player) — a limited round of authenticated checks. No data was modified, no other user accounts were attacked, and no brute-force or denial-of-service testing was performed.

Overall verdict: the most serious confirmed issue is unauthenticated, non-ownership-checked access to character data (broken access control). Several configuration weaknesses compound the risk. Two strong positives stand out: (1) no hardcoded API keys or secrets exist in the client code (all ~640 KB of JavaScript and the HTML were scanned), and (2) the privileged debug and admin endpoints correctly enforce an admin role — these were initially suspected to be unauthenticated but were verified to be protected (see the Corrections note below).

### 1.2 Corrections From the Initial Pass (transparency)

An early, unauthenticated-only pass suspected that `/api/debug/command` and `/api/debug/last-turn` were unauthenticated, because requests reached a 404 `"Character not found"` response instead of being rejected for missing credentials. Re-testing against a real character ID disproved this: those endpoints return 403 `"Admin role required"` for existing characters, both without a token and with a valid non-admin token. The 404 was simply an existence check that runs before the authorization check. The debug endpoints are therefore correctly protected and are not a vulnerability. This correction is included deliberately — verification against real objects matters, and the initial differential-response heuristic produced a false positive.

## 2. Scope and Methodology

- **Target:** `https://aigm-dev.studio-colorbox.com` (development environment)
- **Date:** 1 June 2026
- **Test account:** `wojtek` (`user_id` 1016, role `player`, non-admin)
- **Approach:**
- Retrieval and static analysis of all client assets (`app.js` ~517 KB, `multiplayer_ui.js`, `voice.js`, `teal.js`, `clog.js`, `dice.js`, HTML, CSS).
- Secret scanning (AI/cloud provider keys, JWTs, generic credential patterns).
- HTTP response-header review (security headers, CORS, TLS posture).
- Authentication/authorization testing of sensitive endpoints, validated against real object IDs (not just non-existent ones).
- A single, minimal IDOR confirmation using the low-sensitivity gold field.
- **Not performed:** data-modifying exploitation, access to third-party personal data beyond a single low-sensitivity integer, ID range enumeration, brute-force, and DoS. Active probing was halted when the backend began returning 502s (finding I1).

## 3. Detailed Findings

### 3.1 H1 — Unauthenticated, non-ownership-checked character data access (High)

**Type:** Broken Access Control / Insecure Direct Object Reference (IDOR)

**Description.** Character data endpoints return data for a character that the caller neither owns nor is authenticated to access. The `/api/characters/{id}/gold` endpoint was confirmed to respond successfully with no authentication token at all and without verifying ownership.

**Evidence.** The test account’s only character is id 1132. Character 1131 belongs to a different user, yet:

```http
GET /api/characters/1131/gold
Authorization: <none>

HTTP/1.1 200 OK
{"ok":true,"data":{"gold_gp":0}}
```

```http
GET /api/characters/99999999/gold
Authorization: <none>

HTTP/1.1 404 Not Found
{"detail":"Character not found"}
```

A real, non-owned character returns 200; a nonexistent one returns 404. The endpoint performs neither authentication nor an ownership check.

**Impact.** Any anonymous user can read other players’ character data by ID. The confirmed exposure is low-sensitivity (a gold integer), but the access-control gap is the concern: the same missing-check pattern plausibly affects sibling endpoints (`/api/characters/{id}/spells`, `/api/inventory/{id}`, etc.). Full breadth was not enumerated — testing was halted to avoid stressing the dev backend (see I1) and to avoid reading third-party data.

**Remediation.** Require authentication on all character/inventory data routes; derive the user from the JWT; enforce that the requested resource belongs to the authenticated user (or that the user is a GM/admin for that campaign). Apply the fix as shared middleware so every `/api/characters/{id}/*` and `/api/inventory/{id}` route is covered uniformly.

### 3.2 H2 — Permissive CORS with credentials (High)

**Type:** Security Misconfiguration

**Description.** API responses are returned with a wildcard origin and credentialed access enabled.

**Evidence.**

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization, X-Ollama-Base-Url, X-UI-Trace-Id
```

**Impact.** Any malicious website can script requests against the API and read responses. Combined with bearer tokens kept in `localStorage` (M3) and the unauthenticated data access in H1, this broadens the reach of any token leak or cross-site attack.

**Remediation.** Restrict `Access-Control-Allow-Origin` to the real front-end origin(s); only emit `Access-Control-Allow-Credentials: true` for those exact origins — never together with `*`.

### 3.3 M1 — /api/health unauthenticated information disclosure (Medium)

**Type:** Information Disclosure

**Description.** The unauthenticated health endpoint reveals backend and infrastructure detail.

**Evidence (abridged).**

```text
llm.provider = openai
llm.base_url = https://api.openai.com
llm.model = gpt-5.4
llm.model_count = 118 (full list of 118 model names returned)
loki.url = http://192.168.1.61:3100   <-- internal IP / log server
```

The API key itself is not disclosed (good), but the response leaks internal infrastructure topology and the backing LLM account’s scope.

**Remediation.** Require authentication for the detailed health payload, or return a minimal `{"status":"ok"}` to anonymous callers and keep verbose diagnostics behind admin auth.

### 3.4 M2 — Missing security headers; no HTTPS redirect / HSTS (Medium)

**Type:** Security Misconfiguration

**Description.** No `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, or `Strict-Transport-Security` headers are present, and plain `http://` is served with `200 OK` and no redirect to HTTPS.

**Impact.** Enables clickjacking, MIME-type sniffing, and protocol downgrade / man-in-the-middle attacks. The absence of CSP also removes the main mitigation for token theft via XSS (see M3).

**Remediation.** Force HTTPS (`301` → HTTPS), add `Strict-Transport-Security`, a strict `Content-Security-Policy`, `X-Frame-Options: DENY`, and `X-Content-Type-Options: nosniff`.

### 3.5 M3 — JWT access and refresh tokens stored in localStorage (Medium)

**Type:** Insecure Credential Storage

**Description.** Both `aigm_access_token` and `aigm_refresh_token` are persisted in `localStorage`, readable by any JavaScript on the page. Login confirmed a 7-day (`expires_in: 604800`) access token plus a refresh token are issued and stored this way.

**Impact.** With no CSP (M2), a single XSS leads to full, persistent account takeover — the refresh token lets an attacker continually re-mint access tokens.

**Remediation.** Store tokens in `HttpOnly`, `Secure`, `SameSite` cookies (particularly the refresh token) and deploy a strict CSP.

### 3.6 L1 — Object/user existence enumeration (Low)

Unauthenticated requests distinguish existing from non-existent characters via differential responses (`403/200` for real IDs vs `404` for missing ones). This allows enumeration of valid character IDs.

**Remediation:** return a uniform `404/403` for unauthorized access regardless of existence.

### 3.7 L2 — Client-supplied user_id (Low)

The client passes `user_id` in many requests (query string and bodies). Where the server independently validates identity from the JWT this is harmless, but H1 shows at least one route omits that validation.

**Remediation:** never trust client-supplied identity; derive it solely from the authenticated token and ignore any `user_id` in the request.

### 3.8 L3 — Possible account / email enumeration at registration (Low)

Registration requires an `invite_code` and the invite-info endpoint can return the invited email address; response differences may permit enumeration. Impact was low in testing.

**Remediation:** keep registration/invite responses uniform.

### 3.9 I1 — Backend instability under light load (Informational)

During normal, low-volume testing the backend returned `502 Bad Gateway` across all API routes for a short period (static assets continued to serve), then recovered on its own. This suggests fragile error handling or insufficient worker resilience — a single malformed/unauthorized request may be enough to disrupt the service.

**Remediation:** add robust exception handling, request timeouts, and worker auto-restart; investigate logs for the crash trigger.

## 4. Positive Observations

- No hardcoded secrets in any client asset — all JavaScript, HTML, and CSS were scanned for AI/cloud provider keys, JWTs, and generic credential patterns.
- Debug endpoints enforce an admin role — `/api/debug/command` and `/api/debug/last-turn` return `403 "Admin role required"` for real characters, both unauthenticated and with a non-admin token. (Verified, not assumed.)
- Admin endpoints enforce a separate admin token — `/api/admin/*` returns `401 "Invalid admin token"` for a normal player’s access token; no privilege escalation via the standard session was possible.
- No exposed sensitive files — `.git/`, `.env`, server source, source maps, and database backups are not reachable (the SPA catch-all returns `index.html` for unknown paths; verified the 200s were the index page).
- The OpenAI API key is not leaked by the health endpoint.
- Login returns a generic error (`Invalid credentials`), avoiding user-enumeration at the login step.
- Server banner (`openresty`) discloses no version.

## 5. Recommended Remediation Priority

1. **H1** — Add authentication + ownership enforcement to all character/inventory data routes via shared middleware. (Highest priority — anonymous cross-user data access today.)
2. **H2** — Remove the CORS wildcard-with-credentials configuration.
3. **M3 + M2** — Move tokens to `HttpOnly` cookies; add CSP, HSTS, and an HTTPS redirect.
4. **M1** — Trim the `/api/health` payload for anonymous callers.
5. **L1 / L2 / I1** — Uniform error responses, server-derived identity, and backend resilience.

## 6. Limitations

Authenticated testing used a single non-admin player account and was deliberately narrow: one IDOR confirmation on a low-sensitivity field, no ID enumeration, and no data modification. The full breadth of H1 across sibling endpoints, GM/admin campaign authorization, and write-path access control were not exhausted and are recommended for a follow-up engagement (ideally against a staging copy with seeded test data, so resilience issues like I1 do not affect a shared instance).

This assessment was conducted with the owner’s authorization and limited to the scope described above. The absence of a finding in a given area is not a guarantee that no vulnerability exists there.
